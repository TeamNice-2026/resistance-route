# 機能仕様 — 確定した振る舞いと検証項目

この文書は「何をできるようにするか」を整理する。細かなDBカラム名、外部API、画面見た目は未確定であり、各機能の着手前に相談して確定する。

## 1. 権限【合意済みの方針】

| 操作 | ゲスト | ログイン済み |
| --- | --- | --- |
| 地図・公開おすすめ道の閲覧 | 可 | 可 |
| 現在地表示・徒歩ルート検索 | 可 | 可 |
| ルート比較・経路線の表示 | 可 | 可 |
| GPS記録のサーバー保存・履歴一覧 | 不可 | 本人のみ |
| おすすめ道の投稿・削除 | 不可 | 本人のみ |
| 「参考になった」の評価 | 不可 | 可 |
| 通行確認への記録反映 | 不可 | 有効な本人記録に対し可 |
| アカウント情報・データ削除 | 不可 | 本人のみ |

「ゲストでGPS現在地を表示できる」と「ゲストでGPS履歴をサーバー保存できる」は別の機能として扱う。

## 2. 主要機能

| ID | 機能 | 必須動作 |
| --- | --- | --- |
| F-01 | 地図 | 現在地・対象エリア・公開投稿区間を表示 |
| F-02 | 学校へ行く | 現在地から学校への徒歩経路を検索 |
| F-03 | 目的地検索 | 対象エリアの任意目的地を設定 |
| F-04 | 経路比較 | 最短候補と学生情報を加味したおすすめ候補を比較 |
| F-05 | ナビ表示 | 経路線とGPS現在地を継続表示 |
| F-06 | 認証 | 登録・ログイン・ログアウト |
| F-07 | GPS記録 | 明示的な開始/終了、画面表示中のみ記録 |
| F-08 | GPS補正 | 精度不足・異常な位置ジャンプの抑制 |
| F-09 | 履歴 | 自分の記録一覧・地図表示・削除 |
| F-10 | 投稿 | 自分のGPS履歴区間からのみ公開ルートを生成 |
| F-11 | 参考評価 | 1ユーザーが1投稿を重複評価しない |
| F-12 | 通行確認 | 他ユーザーの実走区間との重なりを判定 |
| F-13 | 確認状態 | 新規/未確認とコミュニティ確認済みを区別 |
| F-14 | 快適スコア | 実際に存在する候補経路を説明可能な基準で比較 |

## 3. ルート検索

- 学校へのルート検索を目立つ主要ボタンにする。
- 目的地は対象エリア内を基本とし、歩行専用のルート探索を使う。
- 表示対象は地図上のルート線、距離、所要時間、候補比較の理由。
- 最短ルートとおすすめルートが同じ場合は**同じであることを表示**する。違うルートがあると偽らない。
- 外部APIの応答なし・経路なし・位置情報拒否・エリア外のときは原因別に案内する。

## 4. GPS実走記録

- 記録するのはユーザーが「開始」を押したセッションのみ。
- GPS現在地・測位精度を確認し、記録中であることを常に示す。
- 停止後、自分の履歴に線として表示できる。
- 記録精度が極端に低い・ほぼ点がない場合は投稿を許可しない。
- Webブラウザではページが閉じた状態や画面ロック中の記録は保証しない。
- データ削除時に関連する投稿・通行確認がどう扱われるかは詳細設計で決める。

## 5. おすすめ道投稿

**元データ:** ログインユーザー自身の実走GPS履歴。自由描画は禁止。

手順：履歴選択→始点/終点の区間選択→公開区間のプレビュー→1個以上のタグ選択→任意コメント→投稿。

**初期タグ案:** 近道、人が少ない、信号が少ない、静か、歩きやすい、屋根が多い、夜でも明るい。

**状態:** 投稿後は即時に公開し、「新規ルート／未確認」扱い。別ユーザーの有効な実走確認に応じて「コミュニティ確認済み」へ変える。

「人が少ない」「夜でも明るい」などは主観的な投稿であって客観的データの保証ではない。

## 6. コミュニティ評価

- 「参考になった」は人気・有用性の評価。GPS通行確認と混同しない。
- 同じ利用者が同じ投稿を繰り返し評価・確認して数を水増ししない。
- 自分の投稿への自己評価は行わない案。
- 実走確認の具体的な閾値・投稿区間との一致方法は [gps-and-routing.md](gps-and-routing.md) の**暫定設計**を参照。
- 公開済み投稿の通報・非表示対応はプライバシー・誤情報対策として設計するが、本格的な管理画面は発展機能にできる。

## 7. 異常系・境界条件

- GPS権限拒否、GPS非対応、HTTPSでないページ
- accuracy悪化、測位停止、GPSの異常ジャンプ、記録中のページ離脱
- 目的地が対象エリア外、検索結果なし、ルートAPI利用制限
- 投稿区間が短すぎる、記録点が少ない、校地・私有地に見えるルート
- 二重投稿・二重評価、複数人による重複確認、削除済み投稿への操作
- ログイン期限切れ、通信切断、API障害、DB接続失敗

いずれもユーザーへの説明を用意し、**黙って成功扱いにしない**。

## 8. 機能別Issueの作り方

この機能表は**Issue一覧ではない**。個別の機能について設計相談が終わり、画面/API/DBの受入条件が確定した**実装着手時**に、その範囲をGitHub Issueへ登録する。
