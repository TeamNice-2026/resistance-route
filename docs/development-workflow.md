# 開発運用ルール — Resistance Route

**対象:** TeamNice-2026の4人全員 / ChatGPT・Claudeでの設計 / Codex・Claude Codeでの実装  
**完成目標:** 2027年2月

## 1. 基本方針と責任分担

**設計相談 → 仕様確定 → Issue作成 → 実装用プロンプト → featureブランチで実装・テスト → PR作成 → ChatGPTとプロジェクト管理者による最終確認 → 管理者の指示でマージ** の順に進める。

| 役割 | 担当 | 責任 |
| --- | --- | --- |
| 仕様決定者 | 機能の提案者・必要な関係担当者 | 目的、範囲、受入条件を確定する |
| Issue担当 | 仕様提案者（AI支援可） | 確定仕様をIssueへ反映し、変更履歴を残す |
| 実装担当 | Issueに割り当てたメンバー | Codex / Claude Codeの成果物を確認し、テスト・PRを作る |
| 技術レビュー支援 | ChatGPT（必要に応じてClaude） | PRの差分、テスト・CI、仕様適合性、リスクを確認・報告する |
| 最終判断・マージ責任者 | **プロジェクト管理者（ユーザー本人）** | レビュー結果を見て採否を判断し、明示的にマージを許可する |

**他メンバーのレビューやGitHub Approveは必須にしない。** 必要なときだけ任意で追加する。ChatGPTのレビューはGitHubアカウントによる独立したApproveとは異なり、**責任者の最終判断を代替しない**。PR作成者が管理者本人でも、自己Approveを必須条件にしない。

通常は管理者がGitHub上でマージする。管理者が**対象PRを指定し、「問題なければマージして」と明示的に依頼した場合**には、ChatGPTが差分とCIを確認した上でGitHub連携からマージしてよい。曖昧な依頼や条件を満たさない場合、ChatGPTは勝手にマージしない。Codex / Claude Codeには自動マージを許可しない。

## 2. 標準フロー

1. **設計相談:** ChatGPT / Claudeへ機能の目的・利用者・正常系・異常系・画面・API・DB・非対象・検証方法を相談する。
2. **仕様合意:** 不明点を解決し、関係する担当者間でAPI・DBなどの境界を合意する。未確定なら `status:design` 。
3. **Issue確定:** 合意した仕様をIssueへ登録し、受入条件・担当・依存関係・対象外・検証方法を明記する。
4. **実装準備:** Definition of Ready（§3）を満たしたIssueを `status:ready` に変更する。担当者は最新の `main` からfeatureブランチを切る。
5. **実装依頼:** `docs/ai-implementation-prompt-template.md` からIssue用プロンプトを作成し、Codex / Claude Codeに渡す。着手時は `status:in-progress` 。
6. **実装・テスト:** 担当者は差分を読み、テスト・型チェック・ビルド、必要な手動/実機テストを実施する。作業途中のDraft PRも利用可能。
7. **PR提出:** PR本文にIssue・変更範囲・検証結果・リスクを記載。Ready for reviewでCI成功を確認したら `status:review` に変更する。
8. **最終確認:** ChatGPTが差分・設計整合性・CI・セキュリティをチェックし、管理者に結果を報告。管理者も差分・必要な動作・受入条件を確認する。問題があれば `status:in-progress` に戻して修正する。
9. **マージ:** **管理者の明示的な許可**のもと、管理者（または指定されたChatGPT）がSquash and mergeする。 `Closes #番号` でIssueがClosedになったことと `main` のCIを確認する。

## 3. Definition of Ready（着手条件）

- [ ] 目的・ユーザー・解決すべき課題が明確
- [ ] 実装範囲と実装しない範囲が明確
- [ ] 画面・API・DBへの影響と関連担当者が明確
- [ ] 依存するIssue・外部サービスと技術的制約が整理されている
- [ ] 正常系・異常系・権限拒否を含む検証可能な受入条件がある
- [ ] GPS・認証・投稿の場合、プライバシー・アクセス権を定義
- [ ] 曖昧な設計判断を実装AIへ丸投げしていない

## 4. Definition of Done（マージ条件）

- [ ] Issueの受入条件を満たす（変更する場合はIssueを修正し合意する）
- [ ] 関連する自動テスト・型チェック・ビルドが成功
- [ ] GitHub ActionsのCIが成功（例外は責任者が理由を記録したときのみ）
- [ ] 実装者が差分を確認し、必要な手動/スマホ実機テストを済ませた
- [ ] API・DB・設計に変更があればドキュメントも修正済み
- [ ] 秘密情報・個人情報・実GPS生ログ・生成物をコミットしていない
- [ ] **ChatGPTによる差分・テスト・仕様整合性のチェック結果を確認した**
- [ ] **管理者本人が最終的に問題なしと判断し、マージを許可した**
- [ ] 未解決の重要な問題・レビュー指摘がない

**他のメンバーによるApproveは必須条件ではない。** ただしGPS・認証・位置情報などの重要機能では、管理者の判断で追加レビューを依頼してよい。

## 5. Issue管理・ステータス

Issueには背景・詳細仕様・実装範囲・非対象・関連する画面/API/DB・受入条件・テスト・担当者・依存Issueを記載する。原則1 Issue＝1つのレビュー可能な単位とする。

- `status:design`：設計相談中
- `status:ready`：仕様確定・着手可能
- `status:in-progress`：実装・テスト・修正中
- `status:review`：PRがReady for review、CI成功、最終確認待ち
- `status:blocked`：外部要因や未解決事項で停止

ステータスラベルは**1 Issueにつき1種類のみ**とし、マージ後にIssueをClosedにする。種類ラベルは `type:feature`、`type:bug`、`type:docs`、`type:chore` を想定（GitHub上へのラベル登録は別作業）。

仕様変更が発生したら、**実装より先にIssueの受入条件を修正**し、理由をコメントで残す。

## 6. Git・PRのルール

- 最新の `main` から `feature/issue-12-current-location`、`fix/issue-23-gps-jump` などのブランチを作る。
- **`main`への直接pushは禁止。** PRとCIを通す。
- PRは原則1 Issueにつき1件。本文に `Closes #番号`、変更点、テスト結果、既知の制限を記載。
- Draft PRは作業途中の共有に使用可能。Draft/CI未完了ではレビュー完了扱いにしない。
- 検証不十分・重大な仕様逸脱・機密情報漏えいが疑われる場合、マージせず修正する。
- マージは原則Squash and merge。AI実装エージェントが無断でマージすることは禁止。

## 7. AI支援の使い分け

**ChatGPT / Claude（設計）:** 必要事項を質問して仕様を確定する。合意前にIssueを勝手に確定しない。  
**Codex / Claude Code（実装）:** Issueと `AGENTS.md`・ `CLAUDE.md`（該当時）・関連設計を読み、指定範囲を実装・テストし、PRまで準備する。  
**ChatGPT（レビュー）:** ユーザーから依頼されたPRについて差分・CI・受入条件を確認し、リスクと判断根拠を報告する。**ユーザーが対象PRのマージを明示的に依頼し、条件を満たしたときだけマージ可能。**

いずれのAIも、無断の仕様拡張、広範囲の改変、API/DBの破壊的変更、秘密情報の出力を行わない。

## 8. 共有・障害時の対応

API/DBなど共有仕様を変えるときは関係者に知らせる。行き詰まったIssueは `status:blocked` とし、再現手順・匿名化ログ・試したことを残す。チャットだけに重要な設計決定を閉じ込めない。

## 9. GitHubでの強制設定について

チーム運用方針とGitHubで技術的に強制できる条件は別。利用可能なら「PR必須」「CI成功必須」を設定し、**他人のApprove必須は設定しない**。管理者のみマージ可能という権限制限はOrganizationのプランと設定に依存するため、強制できない場合でも運用ルールを守る。
