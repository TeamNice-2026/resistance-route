# 開発運用ルール — Resistance Route

**適用対象:** TeamNice-2026の4人全員および実装支援AI  
**最終判断者:** プロジェクト管理者（ユーザー本人）  
**完成目標:** 2027年2月

## 1. 最も重要な原則：Issueは実装の直前に作る

**設計相談中にGitHub Issueを作らない。** まずChatGPT / Claudeと対話し、機能の仕様、非対象、異常系、受入条件、担当範囲、API/DBへの影響を詰める。

仕様に合意し、**Codex / Claude Codeへ実装を任せるタイミング**で初めてIssueを作成する。Issue番号はその時点で決まり、それを使ってAI実装用プロンプトとブランチ名を作る。

事前の「開発予定一覧」は docs/project-requirements.md / docs/roadmap.md 等で管理し、**予定段階のIssueをまとめて先行起票しない**。

### 例外

リポジトリの初期準備、ドキュメント統合、ローカルクローンなど、**コード機能実装前の準備作業**にはIssue作成を必須としない。GitHubの変更が必要な場合は作業ブランチからPRを作り、最終確認後にマージする。単なるローカルのクローン・Docker起動はPushやPRを行わずに作業を完了してよい。

## 2. 標準フロー

1. **設計相談:** 各メンバーがChatGPT / Claudeに「○○を作りたい。必要事項を質問してください」と依頼。相談中はIssueを作らない。
2. **仕様確定:** 目的、画面、API/DBへの影響、正常・異常系、実装対象外、受入条件を合意。合意事項はdocsに反映するか、確定したIssue本文に漏れなく転記する。
3. **Issue作成:** **Codex / Claude Codeへ実装を引き渡すと決まった段階**でAIへIssue作成を依頼。内容・担当・完了条件を人間が確認する。
4. **実装指示:** Issue番号を含む実装用プロンプトを docs/ai-implementation-prompt-template.md から作成する。
5. **作業ブランチ:** 最新のmainから feature/issue-番号-概要 などのブランチを作成して実装する。Issueは status:in-progress（ラベル登録後）。
6. **実装・テスト:** Codex / Claude Codeが変更と自動テストを実行。担当者が差分・機能・必要な実機テストを確認する。
7. **PR作成:** 実装AIはPR作成まで行い、**マージは行わない**。PRにIssue番号、変更点、テスト結果、未解決事項を記載する。CI成功後 status:review。
8. **最終確認:** ChatGPTが差分・CI・仕様整合性・リスクを確認し、管理者が結果を踏まえて最終判断。問題があれば担当者へ修正依頼する。
9. **マージ:** 管理者が対象PRのマージを明示的に許可したときだけ、管理者自身または指定したChatGPTがSquash and mergeし、IssueがClosedになったか確認する。

他メンバーのPull Requestレビュー・GitHub Approveは**必須ではない**。必要なときは任意で依頼できる。

## 3. 役割

| 役割 | 責任 |
| --- | --- |
| 設計相談者（4人のいずれか） | 仕様の目的・範囲と受入条件を対話で確定 |
| ChatGPT / Claude（設計） | 不足要件を質問し、選択肢を比較し、合意内容を文書化 |
| Issue登録の依頼者 | 実装に着手すると決まったときにAIへIssue作成を依頼 |
| 実装担当者（4人のいずれか） | Codex / Claude Codeの作業を監督し、動作と差分を検証 |
| Codex / Claude Code（実装） | 指定Issueだけ実装し、テスト後にPRまで作成 |
| ChatGPT（レビュー） | 依頼されたPRの技術チェック。判断根拠・問題点を報告 |
| プロジェクト管理者 | 最終採否の判断とマージ許可。重要な仕様変更の承認 |

AIによるレビューは独立したGitHub Approveではない。**人間である管理者の最終判断に従う**。

## 4. Issueの作成条件（Definition of Ready）

次の条件が揃うまで、実装用Issueは作成しない。

- [ ] 目的・対象利用者・期待する挙動が説明できる
- [ ] 実装することと実装しないことが分かれている
- [ ] 関係する画面・API・DB、依存する機能を洗い出した
- [ ] 正常系・異常系・権限拒否等の受入条件を具体化した
- [ ] テスト方法と完了判断の方法が明確
- [ ] GPS・認証・投稿機能なら個人情報・アクセス権の扱いを検討した
- [ ] 作業担当と着手の意思が決まっている

1 Issueを、原則として1人または1つの独立した作業単位にする。巨大な機能は設計確定後に複数Issueへ分割する。

## 5. 完了条件（Definition of Done）

- [ ] Issue本文の受入条件を満たしている
- [ ] テスト・型チェック・ビルド・CIが成功
- [ ] 必要なスマホ実機の確認・例外系の確認を実施
- [ ] 実装担当者がAIの変更差分を読んだ
- [ ] API/DB等の変更を関連docsへ反映
- [ ] 秘密情報、個人情報、GPS生ログをコミットしていない
- [ ] ChatGPTがPR差分とCIと仕様を確認した
- [ ] 未解決の重大な問題がない
- [ ] 管理者が最終的にマージを許可した

## 6. Issueラベル（案）

GitHub上に実際のラベルが登録されているかは別途確認する。

| ラベル | 使うタイミング |
| --- | --- |
| status:ready | 設計確定後にIssueを作成し、実装待ち |
| status:in-progress | 実装中／修正中 |
| status:review | Ready for reviewのPR作成とCI成功後 |
| status:blocked | 着手後に未解決の問題が発生 |

**status:designを理由に設計中からIssueを起票しない。** IssueのOpen/Closedは作業の存在と完了を表す。ステータスラベルは1 Issueにつき1つとする。

種類は type:feature / type:bug / type:docs / type:chore 等を想定する。

## 7. GitHub運用

- mainへ直接pushしない。最新mainからfeature/issue-12-current-location等を切る。
- 原則1 Issueに1 PR。PR本文に Closes #番号 とテスト・制限を記載する。
- API・DBの共有仕様変更は関連担当者と合意し、Issue本文・docsを更新する。
- Draft PRやCI失敗を最終確認待ちとは扱わない。
- マージは原則Squash and merge。
- Codex / Claude CodeはPushとPRまで。ユーザーからの明示的な許可なしにマージしない。
- 例外となるIssueなしの初期準備PRは、対応Issueなしと明記してよい。
- アカウント権限やブランチ保護設定の自動強制可否はGitHubのプランに依存する。技術的に強制できない設定はチーム規則で守る。

## 8. 情報共有・仕様の更新

- **現在の合意**は docs/decision-log.md、要件は docs/project-requirements.md を参照。
- 未決定事項はチャットの質問・回答で解決してから実装する。
- 作業途中で仕様変更した場合はIssueを修正し、変更理由を残す。
- 各PRで変更された画面・API・DBに対応するdocsを更新する。
- 他人の作業ファイルをAIが無断で広範囲に変更しない。
- 本番に公開するまでの実GPSデータやパスワードはGit・Issue・PRへ記載しない。
