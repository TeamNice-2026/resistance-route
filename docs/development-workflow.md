# 開発運用ルール — Resistance Route

**対象:** TeamNice-2026の4人全員 / ChatGPT・Claudeによる設計支援 / Codex・Claude Codeによる実装支援  
**完成目標:** 2027年2月  
**原則:** 仕様を合意してからIssue化し、作業ブランチで実装し、二段階の人間レビューを経て `main` に統合する。

## 1. 役割と最終決定権

| 役割 | 担当 | 責任 |
| --- | --- | --- |
| 依頼者 / 仕様決定者 | 機能の提案者と関係担当者 | 目的、対象、完了条件を対話で固める |
| Issue管理者 | 提案者（AI支援可） | 決定内容をIssueへ正確に記録し、変更時に更新 |
| 実装担当者 | Issueに割り当てたメンバー1名 | AIの実装結果を自分で確認し、テスト、ブランチ、PRを管理 |
| 一次レビュアー | **実装担当者以外のメンバー1名以上** | 仕様・差分・テスト・機密情報を確認し、GitHub上でApproveまたは修正依頼 |
| 最終承認・マージ担当 | プロジェクト管理者（今回の合意では依頼者本人） | 一次レビュー後に最終確認し、問題なければ `main` へマージ |

最終マージ担当は当面1名。欠席などで代行が必要な場合は、チーム内で代理を明示してから変更する。  
**重要:** GitHubではPR作成者は自分自身のPRにApproveできない。管理者本人が実装者の場合は「別メンバーのApprove」→「本人が最終チェックしてマージ」とし、本人のApproveレビューを必須条件にしない。

## 2. 標準フロー（全機能共通）

1. **設計相談:** ChatGPT / Claudeと、目的、利用者、UI、API/DB、例外、非対象、テスト観点を対話して固める。
2. **仕様の合意:** メンバーと依存先担当者が受入条件を確認する。未確定事項がある場合はIssueを `status:design` にする。
3. **Issueの確定:** AIにIssue草案またはGitHubへの登録を依頼し、最終的には担当者が内容を照合する。担当、優先度、依存関係、対象外、完了条件を記載する。
4. **着手可能:** Definition of Ready（§3）を満たしたら `status:ready` 。実装担当がブランチを切り、着手時 `status:in-progress` 。
5. **実装指示:** Issue番号、ブランチ、変更範囲、参照仕様、必要テスト、禁止事項を含むプロンプトをCodex / Claude Codeへ渡す。テンプレートは `docs/ai-implementation-prompt-template.md` 。
6. **実装と確認:** 担当者はAI生成差分を自分で読み、必要なテストと手動確認を実施する。必要ならDraft PRを先に作成してもよい。
7. **レビュー依頼:** テスト・CIが成功し、PR説明と自己チェックを記入してReady for reviewにしたら `status:review` 。別メンバーへ一次レビューを依頼する。
8. **一次レビュー:** 実装者以外が差分・挙動・設計適合性を確認し、問題なければGitHubの**Approve**、問題があれば**Request changes**。修正時は `status:in-progress` に戻す。
9. **最終確認:** 管理者が一次Approve、CI、会話の解決、実際の動作、Issue受入条件を確認する。管理者がPR作成者でない場合は可能なら自身もApproveを記録する。
10. **マージ:** **管理者のみ**が `main` へSquash and mergeする。本文の `Closes #番号` でIssueが閉じたことを確認する。手動で閉じる場合はPRリンクを残す。

AIに自動マージや `main` への直接pushを指示してはいけない。レビューの責任は常に人間が負う。

## 3. Definition of Ready（実装開始条件）

- [ ] なぜ作るか、誰が使うかが明確
- [ ] 実装範囲と**実装しないこと**が明確
- [ ] 画面、API、DBなどの変更点と担当範囲が明確
- [ ] 外部依存・他Issueとの関係が確認されている
- [ ] 正常系・異常系・権限拒否などの**具体的な受入条件**がある
- [ ] GPS・認証・投稿の場合、個人情報やセキュリティ上の扱いを定義
- [ ] 想定が曖昧な点を担当者だけで勝手に補完しない状態

## 4. Definition of Done（マージ条件）

- [ ] Issueの受入条件を満たす（満たさない項目はIssue変更と合意が必要）
- [ ] 対象機能の自動テストと必要な手動テストが成功
- [ ] GitHub Actionsの必須チェックが成功（CI障害時は理由と代替検証を明記し、管理者が判断）
- [ ] 変更差分を実装担当者が確認済み
- [ ] API/DB/設計変更をドキュメントへ反映済み
- [ ] 機密情報・実際のGPS生ログ・依存フォルダをコミットしていない
- [ ] **実装者以外のメンバーから一次Approveが1件以上**
- [ ] 指摘事項を解消し、未解決のレビューコメントがない
- [ ] **管理者が最終承認し、自分でマージを実行**

GPSなどブラウザ・スマートフォン依存機能は、CI成功のみで完成とせず対象端末での実機確認を必要とする。

## 5. GitHub Issueのルール

### Issueに必ず含める内容

- 背景・目的
- 詳細仕様 / ユーザーフロー
- 対象範囲・対象外
- API・DB・画面の影響
- 受入条件（チェックリスト、できるだけ検証可能な表現）
- 担当者と依存Issue
- テスト観点・完了確認方法

1 Issueは原則として1つの独立してレビューできる作業単位とする。巨大なIssueは分割する。  
仕様が途中で変わった場合は、**Issueの内容を先に更新し、変更の理由をコメントに残す**。完了条件が変わるなら関係者と再合意する。

### ラベルの設計（GitHubで別途登録）

| ステータスラベル | 意味 |
| --- | --- |
| `status:design` | 相談・仕様調整中 |
| `status:ready` | 設計確定・実装待ち |
| `status:in-progress` | 実装・テスト・修正中 |
| `status:review` | PR作成済み・CI成功・一次レビュー待ち / 最終確認待ち |
| `status:blocked` | 外部依存・技術的問題で停止中 |

ステータスラベルは**同時に1つだけ**を付ける。PR修正中は `status:in-progress` へ戻す。マージ後はIssueをClosedへ変更する。  
種類は `type:feature`、`type:bug`、`type:docs`、`type:chore` を使用する（こちらも別途GitHub登録が必要）。

ラベル変更は担当者またはAIアシスタントが行ってよいが、実際に条件を満たしていることを担当者が検証すること。

## 6. Git / Pull Request

- **ブランチ:** `feature/issue-12-current-location`、`fix/issue-23-gps-jump`、`docs/issue-24-workflow` など。
- **起点:** 必ず最新の `main` から作成する。別Issueの未マージ差分を混ぜない。
- **コミット:** 原則小さく意味ごとに分ける。秘密情報を追加しない。
- **PR:** 原則1 Issueにつき1 PR。本文に `Closes #12`、変更概要、テスト結果、スクリーンショット、リスク、レビュー担当者を記載する。
- **Draft PR:** 途中共有には利用可能。ただしDraftやCI失敗の状態で `status:review` にしない。
- **マージ:** 管理者がSquash and merge。マージ直後にIssueのClosedと `main` のCIを確認する。
- **例外:** 緊急の修正も原則PRを通す。緊急対応で標準手順を変更する場合は管理者が承認し、事後にIssue・検証結果・対応理由を残す。

## 7. AI利用の共通ルール

**設計支援:** ChatGPT / Claude は不足条件を確認し、勝手に未合意の仕様を決めない。Issue作成依頼があるときだけGitHubに反映する。  
**実装支援:** Codex / Claude Code はリポジトリの `AGENTS.md` と `CLAUDE.md`（該当時）・Issue・関連設計を先に読む。変更対象を守り、テストし、結果と制限を報告する。  
**禁止:** 無断の仕様拡張、広範なリファクタリング、API/DBの破壊的変更、 `main` 直接push、自動マージ、秘密情報・生GPSデータの出力。  
**レビュー:** AIレビューは補助であり、人間の一次Approve・管理者の最終確認を代替しない。

## 8. 相談・判断・障害

- API・DBスキーマなど共有インターフェースの変更は、影響する担当者へ事前相談する。
- 詰まったら `status:blocked` に変更し、再現手順、ログ（個人情報を除く）、試したことをIssueに記載する。
- 仕様決定の経緯はIssueまたはdocsに残す。チャットだけに閉じ込めない。
- 毎週、担当者・Issueの状態・リスク・次に完了する作業を短く共有する。

## 9. GitHub設定上の制約

この文書は**チームの運用方針**であり、GitHubによる強制設定とは別である。 `main` のPR必須、一次レビュー承認、CI必須、直接push禁止をGitHubの設定で強制できる場合は設定する。プランで強制できない場合も同じ運用を人間が守る。最終マージ担当者をシステム上で限定できるかはOrganizationの権限・プランによるため、利用可能な機能を確認して別途設定する。
